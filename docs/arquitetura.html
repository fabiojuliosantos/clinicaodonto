Sistema de gestão clínica

Arquitetura do Odonto

Sistema de controle interno de uma clínica odontológica. O escopo atual cobre gestão clínica e controle de estoque de insumos — pagamento, convênio e plano de saúde são features futuras e não fazem parte do modelo de domínio hoje.

Arquitetura em camadas

O backend (solution Odonto.Backend) segue Clean Architecture com quatro camadas. A regra de dependência é estrita: o Domínio não conhece nenhuma camada externa — é o centro estável do sistema, e tudo aponta para ele.

Odonto.API Controllers, DI, configuração
→
Odonto.Application Services, DTOs, casos de uso
→
Odonto.Domain Entidades, regras, interfaces
←
Odonto.Infrastructure EF Core, repositórios
Domain não depende de ninguém — todas as setas apontam para ele

Odonto.Domain

Entidades, agregados, value objects, enums, regras de negócio e interfaces de repositório. Zero dependência de framework — nenhuma referência a EF Core, ASP.NET ou qualquer biblioteca externa.

Odonto.Application

Casos de uso implementados como Services, orquestração entre agregados, DTOs e interfaces de serviços externos. Depende apenas do Domain.

Odonto.Infrastructure

Implementação concreta com EF Core: repositórios, migrations, integrações externas. Implementa as interfaces definidas em Domain e Application — nunca o contrário.

Odonto.API

Ponto de entrada: Controllers, injeção de dependência, configuração da aplicação.

Erro de arquitetura

Domain referenciando EF Core (ou qualquer framework) é uma violação direta da regra de dependência e deve ser apontado em code review, independentemente do motivo alegado.

Linguagem ubíqua

O vocabulário do código segue o vocabulário do negócio, em português. Cada termo abaixo tem um único nome canônico em todas as camadas — do Domain ao DTO, ao endpoint, à tabela. Traduções parciais não são aceitas.

Paciente
Quem é atendido. Nome, Cpf, DataNascimento, Telefone, Email.
Dentista
Profissional. Nome, Cro, Especialidade.
Especialidade
Área de atuação — ex.: Ortodontia, Endodontia.
Agendamento
Marcação de horário. Paciente, Dentista, DataHora, Situacao.
Consulta
Atendimento realizado — criada quando um Agendamento é realizado.
Procedimento
O que é feito. Nome, Valor, Duracao.
Prontuario
Histórico clínico do paciente — registros das consultas.
PlanoTratamento
Procedimentos planejados. Paciente, Procedimentos, Situacao.
Insumo
Item consumível de estoque. Nome, Unidade, QuantidadeEstoque, EstoqueMinimo.
MovimentacaoEstoque
Entrada/saída de insumo. Insumo, Tipo, Quantidade, Data.

Ciclo de vida do Agendamento

Agendamento e Consulta são conceitos separados. O atendente marca o horário — gerando um Agendamento — e depois sinaliza o desfecho através das transições de estado.

Agendado → Confirmar() → Confirmado → Realizar() → Realizado
também pode ir para Remarcado / Cancelado a partir de qualquer estado não-terminal

Quando Realizar() é chamado, uma Consulta é gerada e vinculada ao Agendamento. Essa é a única forma válida de criação de uma Consulta no sistema.

Módulo de Estoque de Insumos

Modelagem a confirmar

Módulo novo. O objetivo é saber o que precisa ser comprado, mas a modelagem abaixo é uma suposição inicial — confirmar com o desenvolvedor antes de implementar.

Insumo possui QuantidadeEstoque e EstoqueMinimo. Quando QuantidadeEstoque <= EstoqueMinimo, o item entra na lista de reposição.

MovimentacaoEstoque registra entrada (compra) e saída (consumo), através do enum TipoMovimentacao { Entrada, Saida }.

Fora de escopo

Convênio, plano de saúde, pagamento e faturamento. Não modelar essas áreas no estado atual do sistema, mesmo que pareçam naturalmente relacionadas a Procedimento ou PlanoTratamento.

Convenções de nomenclatura

Português no domínio, inglês na plataforma

Entidades, value objects, enums e métodos de regra de negócio são em português (Paciente, Agendamento.Confirmar(), SituacaoAgendamento.Cancelado). Sufixos de padrão técnico e membros de infraestrutura ficam em inglês (Repository, Service, Validator, Controller, Dto, Id, CreatedAt, UpdatedAt).

Acentuação

Sem acento em identificadores de código (Situacao, Prontuario, Procedimento). Acento é reservado para strings voltadas ao usuário final.

Commits

Conventional Commits, com tipo em inglês e descrição em português, no imperativo. 

feat: adiciona agendamento de consulta
fix: corrige cálculo de duração do procedimento
test: adiciona testes do agregado Agendamento
refactor: extrai validação de Cpf para value object
chore: atualiza pacote do EF Core
docs: documenta regra de ciclo de vida do agendamento

Tipos válidos: feat, fix, test, chore, refactor, docs.

Ambiente

.NET 10. Autenticação Git via SSH — não usar Personal Access Token nem HTTPS com senha. A solution fica em Odonto.Backend/; obj/, bin/ e .idea/ são ignorados pelo Git.

Regra de trabalho com assistentes de IA

Regra fundamental

Assistentes de IA não devem desenvolver código de produção por conta própria. Sem um pedido explícito do desenvolvedor para implementar uma funcionalidade, a atuação deve se limitar a: revisar código, criar testes, gerar mensagens de commit e responder dúvidas.

Em caso de dúvida sobre se uma tarefa envolve escrever código de produção, a IA deve perguntar antes de agir.
